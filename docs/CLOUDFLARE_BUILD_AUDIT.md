# Проверка сборки Supabase для Cloudflare Pages

## Подтверждённые результаты

- Клиент создаётся в `src/cloud/client.ts`. Он читает `import.meta.env.VITE_SUPABASE_URL` и `import.meta.env.VITE_SUPABASE_PUBLISHABLE_KEY`, обрезает пробелы и проверяет публичный ключ через `src/cloud/configuration.ts`.
- Отсутствие обеих переменных приводит к сообщению «сервер аккаунтов не настроен» и `supabase = null`. Неполная или некорректная пара даёт другое сообщение. Подмены имени ключа, загрузки секрета на сервере во время открытия страницы или условий на домен Cloudflare здесь нет.
- Vite встраивает эти значения во время сборки. Проверка с `CF_PAGES=1` и искусственными публичными значениями в окружении процесса подтвердила наличие обоих значений в сгенерированном JavaScript. Переменные процесса имеют приоритет над `.env.local`.
- На момент проверки 26 октября опубликованный `client-2HnudwCv.js` содержит только постоянное сообщение ошибки и `null`. Это состояние опубликованного артефакта, а не только кэш пользовательского браузера. Сам факт наличия значений в интерфейсе Cloudflare не объясняет, почему именно этот процесс сборки их не получил.
- `dist`, `dist-e2e`, `dist-cloud` и `.env.local` исключены из Git. `npm run build` выполняет TypeScript и Vite, не копирует готовые файлы. Локальные браузерные тесты явно очищают Supabase-переменные, но сохраняют результат в отдельную папку `dist-e2e`. Публиковать её нельзя. В GitHub Actions нет шага публикации сайта.
- В проблемном коммите присутствовал `wrangler.toml` с `pages_build_output_dir = "./dist"` без `[vars]`. Лог подтверждает его чтение. Файл удалён, чтобы проект использовал единственный источник конфигурации Pages — панель Cloudflare, где пользователь управляет переменными. Pages Functions в репозитории нет; серверные функции размещаются в Supabase. Публичные ключи не переносятся в Git.

## Настройки для этого репозитория

| Поле                   | Значение                                                      |
| ---------------------- | ------------------------------------------------------------- |
| Root directory         | Пустое поле: корень репозитория, где находится `package.json` |
| Build command          | `npm run build:cloudflare`                                    |
| Build output directory | `dist` (относительный путь без ведущего `/`)                  |
| Node.js                | 22                                                            |
| Vite mode              | `production`                                                  |

В конфигурации Vite `root` и `envDir` теперь привязаны к каталогу конфигурационного файла, `outDir` явно равен `dist`, а перед записью удаляются старые выходные файлы. Переопределение `--outDir` сохраняется для изолированных тестов.

## Защита и диагностика

- Обычная сборка на Cloudflare (`CF_PAGES=1`) и специальная команда `build:cloudflare` завершаются с ошибкой при отсутствующей/невалидной конфигурации. Успешно опубликовать клиент с `null` в этих режимах больше нельзя. Автономный локальный режим также запрещён для облачного выпуска.
- Строка `[easy-learn:build]` выводит корень, каталог env-файлов, выходной каталог, mode, SHA, ветку, наличие каждой переменной и источник (`process`, `env-file`, `missing`). Значения URL и ключа не выводятся.
- Строка `[easy-learn:bundle]` подтверждает, что значения найдены в сгенерированных JavaScript-файлах. Если входы присутствовали, но компиляция их отбросила, сборка завершается с ошибкой.
- В выходную папку добавляется `build-info.json`: время сборки, SHA из Cloudflare/GitHub, mode и булевы флаги `supabaseConfigured` / `supabaseEmbedded`. Ключей, URL сервиса и путей рабочей машины в этом файле нет.
- Для `/build-info.json` задан `Cache-Control: no-store`; файл исключён из precache PWA и из навигационного fallback. Сравнение этого файла на основном домене и уникальном Deployment URL позволяет обнаружить публикацию другого артефакта. В старых deployments файла ещё нет.

## Полученный лог проблемной сборки

Пользователь предоставил полный Build log для коммита `d29d720f79f9b3ff9148c91832121e29854a0f57`:

- Cloudflare читает `wrangler.toml`, выводит `pages_build_output_dir: dist` и `Build environment variables: (none found)`.
- Затем выполняется настоящая команда `npm run build` → `tsc -b && vite build`. Это не пропуск сборки и не публикация закоммиченного `dist`.
- Vite пишет `Generated an empty chunk: "cloud-sdk"`; результат содержит пустой SDK и `client-2HnudwCv.js`. Сравнение с опубликованным модулем подтверждает, что клиент отключён при компиляции.
- `Uploaded 0 files (96 already uploaded)` означает повторное использование файлов с тем же содержимым после новой сборки. Само по себе это не ошибка кэша.
- Исправления с диагностикой в этом коммите отсутствуют. Retry этого deployment повторяет старую версию кода.

Важно: строка `(none found)` находится в блоке чтения Wrangler и сама по себе не является полным списком `process.env`. Она не доказывает, что именно Wrangler удалил переменные из окружения процесса. Удаление необязательного файла устраняет второй источник настроек; фактическое поступление переменных в Vite подтверждается только диагностикой процесса и проверкой результата сборки.

## Как проверить результат исправления

Изменения должны войти в новый коммит; повтор старого deployment их не применит. В сборке нового коммита:

1. Pages использует настройки панели, без корневого `wrangler.toml`.
2. `[easy-learn:build]` показывает SHA нового коммита, `present: true` и `source: "process"` для двух публичных переменных.
3. `[easy-learn:bundle]` и `build-info.json` показывают `supabaseConfigured: true`, `supabaseEmbedded: true`.
4. Если входы не поступили, сборка останавливается до публикации, а диагностическая строка показывает, на каком этапе нарушен путь конфигурации. Для продолжения достаточно прислать эту строку и SHA, без значений ключей.

Документация: [Cloudflare build configuration](https://developers.cloudflare.com/pages/configuration/build-configuration/), [Wrangler configuration and source of truth](https://developers.cloudflare.com/pages/functions/wrangler-configuration/).
