В Edge Functions → Secrets задать `ALLOWED_ORIGINS=https://easy-learn.pages.dev` для функций приложения.

## Локальная проверка без внешних аккаунтов

Нужны Node.js 22+, pnpm 10.34.7, Docker и Chrome для Playwright.

```bash
pnpm install --frozen-lockfile
pnpm supabase:start
pnpm test:cloud
pnpm test:cloud:browser
pnpm test:cloud:delete
pnpm test:cloud:cleanup
```

Локальные проверки используют одноразовые аккаунты и локальную почту Mailpit на http://127.0.0.1:54324. Они не обращаются к production. Edge Runtime исключён из минимального локального запуска; `test:cloud:delete` запускает настоящую функцию отдельно через Deno 2.9.6 и проверяет её на локальном Supabase. После изменения схемы типы клиента обновляются командой `pnpm cloud:types`.

Для ручной работы скопируйте `.env.example` в `.env.local`, укажите URL локального API и его публичный publishable/anon key из `pnpm exec supabase status`, затем запустите `pnpm dev`. Серверный service-role/secret key в `.env.local` и переменные `VITE_*` не помещать.

Для остановки: `pnpm supabase:stop`. Для сброса только локальной базы: `pnpm supabase:reset` — удаляет локальные тестовые данные.

## Supabase: первый внешний проект

1. Создать бесплатный проект в подходящем регионе. Для preview использовать отдельный проект или локальное окружение.
2. Выполнить `pnpm exec supabase login`, затем `pnpm exec supabase link --project-ref YOUR_PROJECT_REF`.
3. Применить SQL: `pnpm exec supabase db push`. Применить сгенерированный `supabase/seed.sql` через SQL Editor, чтобы заполнить допустимые идентификаторы общего каталога. Каталог самих карточек остаётся в статических файлах сайта.
4. В Auth включить подтверждение email и минимальную длину пароля 8 символов. Настроить собственный SMTP, отправителя и шаблоны регистрации/восстановления.
5. Указать Site URL рабочего сайта и разрешённые URL возврата: `https://YOUR_DOMAIN/auth/callback` и `https://YOUR_DOMAIN/auth/callback?type=recovery`. Тестовые домены добавлять в тестовый проект.
6. В настройках проекта взять URL и публичный publishable key. Добавить их в окружение сборки сайта.
7. Развернуть функции: `pnpm exec supabase functions deploy delete-account` и `pnpm exec supabase functions deploy cleanup-images`. Функция сама проверяет пользователя по bearer-токену; браузеру не нужны серверные ключи.
8. Настроить секрет функции `ALLOWED_ORIGINS` со списком доверенных origins через запятую. Не добавлять произвольные wildcard-домены.
9. Проверить вход двумя пользователями, права на файлы и удаление тестового аккаунта на preview перед открытием регистрации.

## Cloudflare Pages

1. Подключить репозиторий через Pages → Create project.
2. Настроить Node.js 22, pnpm 10.34.7, сборку `pnpm build`, выходную папку `dist`.
3. Для каждого окружения сборки задать:
   - `VITE_SUPABASE_URL`;
   - `VITE_SUPABASE_PUBLISHABLE_KEY`.
4. Для preview указать отдельный Supabase-проект. Эти значения встраиваются в браузерную сборку; после изменения нужна пересборка.
5. Выпустить preview и проверить `/login`, `/register`, `/auth/callback`, `/sets/:id`, восстановление пароля, обновление PWA и офлайн-запуск.
6. Указать окончательный домен в Supabase Auth и `ALLOWED_ORIGINS`, затем выпустить production.

Проект использует стандартный SPA fallback Cloudflare Pages при отсутствии корневого `404.html`. Файл `public/_headers` настраивает базовые заголовки и обновление service worker. `wrangler.toml` задаёт папку сборки для CLI.

## Рабочая модель данных

- Гостевая библиотека остаётся в IndexedDB `easy-learn` со схемой v2, совместимой с прежней локальной версией; каждый аккаунт использует `easy-learn-user-USER_ID`.
- Настройки и маркеры каталога разделены по аккаунтам. При выходе личная локальная копия остаётся для последующего входа, но интерфейс переключается на гостевую базу.
- Перенос гостевой библиотеки запускается в настройках явно, после предложения скачать резервную копию. Исходная библиотека сохраняется. При коллизиях личные материалы копируются, чтобы не заменить облачную библиотеку.
- Каждый локальный commit записывает изменения и исходящие операции одной IndexedDB-транзакцией. Повтор операции использует прежний UUID.
- Серверный `apply_sync_batch` применяет всю операцию одной PostgreSQL-транзакцией, определяет владельца по `auth.uid()`, проверяет ссылки и сохраняет квитанцию повтора.
- Протокол первой версии использует представление `sync_records` с ограниченным набором типов и JSONB. Содержимое карточек физически хранится в `sync_record_data`, личный начальный прогресс и ручные отметки — в `card_progress`. `review_events` и `activity_events` предоставляют события для вычисления текущего состояния. Это сохраняет строковые ID и структуры локального приложения. Связи представлены упорядоченными массивами и проверяются сервером.
- Изменения разных полей объединяются. Изменение одного поля на двух устройствах или удалённой записи создаёт конфликт всей операции. Обе версии доступны для скачивания в настройках.
- Повторения и активность передаются событиями. SRS пересчитывается в порядке `(timestamp, id)`, статистика — из импортированного начального состояния и уникальных событий. Время события — время устройства; неверные часы устройства могут влиять на расписание.
- Импортированные исторические повторения включены в начальный прогресс и повторно не воспроизводятся. Резервная копия содержит готовые итоги и изображения, а не токены сессии и очередь.
- Курсор основан на серверной ревизии. Записи удалений и квитанции сохраняются без очистки, поэтому устаревшее устройство не восстанавливает удалённое автоматически. Размер этого журнала нужно контролировать.
- Изображения загружаются в приватный `card-images` по пути `USER_ID/SHA256`, в PostgreSQL хранятся ссылки `storage://...`, локально — data URL для офлайна и экспорта.

## Эксплуатация и оставшиеся проверки перед публичным запуском

- Проверять Database/Storage/Egress и Auth usage в панели Supabase, настроить уведомления о приближении к квотам. Free не превращается в Pro автоматически.
- Сохранять внешние резервные копии перед миграциями и периодически проверять восстановление на отдельном проекте. Пользовательский JSON — копия библиотеки, а не полноценный бэкап Auth и серверной схемы.
- Данные Auth/API не добавлены в кэш service worker; личные изображения хранятся в базе конкретного аккаунта.
- Перед публичным выпуском проверить SMTP, точные redirect URL, функцию удаления аккаунта и production/preview домены. Внешние аккаунты не созданы автоматически.
- Очистка изображений запускается из настроек: удаляются только неиспользуемые файлы старше 7 дней. Серверная блокировка защищает активные ссылки и незавершённые импорты от параллельных изменений. Загрузки перепроверяются при каждой исходящей операции. При удалении аккаунта удаляются все его файлы. Если серверная функция аварийно завершится без `finally`, блокировка останется: оператор должен проверить окончание процесса в логах и вызвать `finish_image_cleanup` с owner/token из `image_cleanup_locks`. Автоматического истечения у блокировки нет, чтобы старый процесс не удалил файл после возобновления записи.
- При длительной эксплуатации потребуется согласованная очистка журнала с полной повторной загрузкой старых клиентов. Текущий протокол принимает до 100 000 изменений и 20 МБ JSON за операцию после выноса изображений в Storage. Операции свыше 100 изменений передаются возобновляемыми частями и становятся видимыми после атомарного применения последней части.
